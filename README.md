# Agile Team Charter
## Evidence
The GrandCaddy project was built using an Agile Team Charter that defined the team’s purpose, shared values, roles, working agreements, and boundaries. The charter focused on the product’s core goals, how the team would collaborate, and how decisions would be made across the project lifecycle. It also established standards for communication and accountability so that the team could work consistently and effectively.

The charter also included a clear definition of done: an item was only finished once it met acceptance criteria, had been reviewed by the team, and had been tested. This helped keep our development process disciplined, reduce rework, and make sure each feature was usable before it moved forward.

## Reflection
This charter was important because it created a shared understanding of how the team should work together. It helped us avoid scope creep and kept the project aligned with user needs, especially in areas such as trust, safety, and ease of use. The result was a more organised workflow, clearer responsibilities, and stronger collaboration throughout the project.

# User Stories and Tasks
## Evidence
The main project story I developed was the Caddy/Helper user story. It focused on the helper journey from registration and profile creation to browsing available tasks, viewing task details, and accepting or rejecting a task. This story was important because it mapped the user’s experience in a realistic and understandable way and helped the team focus on a clear goal.

The story was broken into smaller parts:
- US-2.1: Onboarding flow
- US-2.2: Profile creation
- US-2.3: Browse available tasks
- US-2.4: View task details
- US-2.5: Accept or reject a task

This structure made the work manageable and testable. Each story had acceptance criteria so the team knew exactly what “done” looked like. The main priority was to keep the process simple while still covering the core user journey. By breaking the work into smaller pieces, we were able to plan more effectively and reduce confusion during development.

## Reflection
Writing the user stories helped me understand that requirements must be written from the user’s perspective. It also showed me that tasks should be small enough to be completed and tested in a sprint without becoming overwhelming. This experience improved my understanding of Agile planning and helped me see how clear requirements lead to better design and development decisions.

# Product Backlog
## Evidence
The GrandCaddy product backlog was organised using priority levels based on what was most important for the product. The must-have items included the main customer journey, helper journey, and data requirements needed to support the app. The backlog helped the team stay focused on delivering the most valuable features first and prevented the project from becoming unstructured.

This backlog was refined as the project progressed. The team added trust, verification, and safety requirements after learning more about the real product needs. This showed that backlog management is not static; it evolves as feedback and understanding improves. It also confirmed the value of reviewing priorities regularly during the project lifecycle.

## Reflection
The backlog taught me that prioritisation is more than ordering tasks; it is about deciding what must be built first to create a safe and usable system. The product was designed around trust and usability, and those priorities influenced the way work was scheduled. I learned that a properly maintained backlog supports team alignment and makes it easier to respond to changing requirements.

# Sprint Backlog
## Evidence
The project was completed in four weekly sprint cycles:

| Sprint | Focus | Outcome |
| --- | --- | --- |
| Sprint 1 | Caddy user story | Defined the helper journey and acceptance criteria |
| Sprint 2 | Wireframes | Designed the major screens and profile structure |
| Sprint 3 | Functionality and testing | Added navigation and tested user flow |
| Sprint 4 | Database | Created and connected the database to the application |

Each sprint had a clear goal and a set of tasks to complete. This structure helped the team work progressively and reduced confusion about what needed to be finished before moving on to the next stage.

## Reflection
The sprint backlog showed me how Agile planning works in practice. Each week had a clear purpose, and each purpose built on the previous one. I learned that realistic planning matters, especially in software projects where changing requirements and technical challenges can quickly affect delivery. The sprint structure made progress visible and made it easier for the team to stay organised.
