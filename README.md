# Agile Team Charter
## Evidence
The GrandCaddy project was built using an Agile Team Charter that defined the team’s purpose, shared values, roles, working agreements, and boundaries. The charter focused on the product’s core values: simplicity, accessibility, safety, and trust. Our team agreed that all work should stay on the board, that daily stand-ups would be recorded, and that the team would review changes before finalising them.

The charter also included a clear definition of done: an item was only finished once it met acceptance criteria, had been reviewed by the team, and had been tested. This helped keep our development work focused and ensured that no task was considered done without evidence of quality.

## Reflection
This charter was important because it created a shared understanding of how the team should work together. It helped us avoid scope creep and kept the project aligned with the user needs, especially for older users who needed a simple and safe experience. I learned that a team charter is not just administration; it is a practical tool that guides daily decisions and reduces confusion during development.

# User Stories and Tasks
## Evidence
The main project story I developed was the Caddy/Helper user story. It focused on the helper journey from registration and profile creation to browsing available tasks, viewing task details, and accepting or rejecting a task.

The story was broken into smaller parts:
- US-2.1: Onboarding flow
- US-2.2: Profile creation
- US-2.3: Browse available tasks
- US-2.4: View task details
- US-2.5: Accept or reject a task

This structure made the work manageable and testable. Each story had acceptance criteria so the team knew exactly what “done” looked like. The main priority was to keep the process simple while still creating enough trust for users to feel safe and confident.

## Reflection
Writing the user stories helped me understand that requirements must be written from the user’s perspective. It also showed me that tasks should be small enough to be completed and tested in a single sprint. This was valuable because it made the project easier to plan, easier to explain to the team, and easier to assess against the rubric.

# Product Backlog
## Evidence
The GrandCaddy product backlog was organised using priority levels based on what was most important for the product. The Must-have items included the main customer journey, helper journey, and database functionality. Should-have items included features like reviews, ratings, and payments, while Could-have items included notifications and earnings-related features.

This backlog was refined as the project progressed. The team added trust, verification, and safety requirements after learning more about the real product needs. This showed that backlog management is a living activity and not a one-time document.

## Reflection
The backlog taught me that prioritisation is more than ordering tasks; it is about deciding what must be built first to create a safe and usable system. The product was designed around trust and user safety, so features that affected trust and reliability were ranked above convenience items. This helped me understand why Agile teams continuously refine the backlog as they learn more.

# Sprint Backlog
## Evidence
The project was completed in four weekly sprint cycles:

| Sprint | Focus | Outcome |
|---|---|---|
| Sprint 1 | Caddy user story | Defined the helper journey and acceptance criteria |
| Sprint 2 | Wireframes | Designed the major screens and profile structure |
| Sprint 3 | Functionality and testing | Added navigation and tested user flow |
| Sprint 4 | Database | Created and connected the database to the application |

Each sprint had a clear goal and a set of tasks to complete. This structure helped the team work progressively and reduced confusion about what needed to be finished before moving on.

## Reflection
The sprint backlog showed me how Agile planning works in practice. Each week had a clear purpose, and each purpose built on the previous one. I learned that realistic planning matters, especially for technical work, because database connection issues and testing delays can affect the entire project timeline.

# Agile Logbook
## Evidence
The logbook captured daily stand-up entries for each working day, including:
- what was completed,
- what would be done next,
- what was blocking progress.

The entries from the four project weeks show the project moving from planning to design, testing, and database implementation. The logbook also revealed recurring issues such as simplifying the interface, keeping the team aligned, and managing technical risk.

These daily notes helped document the project as it evolved and gave evidence that the team worked in an Agile and reflective way.

## Reflection
The logbook was one of the most useful parts of the portfolio because it showed real progress over time. By writing my reflections and blockers each day, I noticed patterns in my work and became more aware of risks early. I also learned that honest reporting of obstacles is a strength in Agile work, because it makes problems visible and allows action to be taken before they become bigger issues.
