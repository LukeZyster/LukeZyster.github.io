# 1. Agile Team Charter

## Evidence
The GrandCaddy team charter was built around the project values of simplicity, accessibility, safety, and trust. We agreed on the following:

- Purpose: design and build a platform where elderly users can safely access trusted helpers for everyday tasks.
- Shared values: simple interface, user-friendly design, safety, trust, and accessibility.
- Roles: team members were assigned to customer, helper, and administrator journeys.
- Working agreements: work only on approved backlog items, complete daily stand-ups, review work as a team, and keep scope focused.
- Definition of done: acceptance criteria met, reviewed by the team, works with connected pages, and tested.
- Boundaries: verification, ratings, payment, and notifications were recorded as future requirements.

This shows the team followed a clear Agile structure and kept the project focused on the agreed scope.

## Reflection
The charter helped the team stay aligned and prevented unnecessary work from spreading into unrelated requirements. At first it seemed like paperwork, but it became valuable when the team had to make decisions about scope, simplicity, and trust. I learned that a charter is only useful if it is specific enough to guide decisions. In future, I would make the agreements even more precise and review the charter again after the first sprint.

# 2. User Stories and Tasks

## Evidence
My main contribution was the Caddy/Helper user story.

### User Story 2: Caddy/Helper
As a Caddy, I want to register, create a profile, view available tasks, and accept or reject tasks, so that I can safely and confidently help people in my community.

### Sub-stories
- US-2.1: Simple onboarding flow
- US-2.2: Create a profile
- US-2.3: Browse available tasks
- US-2.4: View task details
- US-2.5: Accept or reject a task

### Acceptance criteria
- Registration must remain simple and clear.
- The profile must include name, picture, description, services, location, availability, experience, rating, and verification status.
- Only open tasks are displayed to helpers.
- An accepted task must be assigned to one helper only.
- Accept and reject actions must be clearly different and confirmed.

### Tasks completed
- Reviewed team notes and started the Caddy user story (14 Jul)
- Defined story structure and elements (15 Jul)
- Finalised story and consulted the team (16–17 Jul)
- Created wireframes for the homepage and profile structure (21–24 Jul)
- Added page functionality and testing (28–31 Jul)
- Created the database and connected it to the application (4–7 Aug)

## Reflection
Writing this user story taught me how important it is to think from the user’s perspective. It also showed me how requirements become technical decisions later in the project, because the profile fields and accept/reject rule directly affected the database design. I learned that acceptance criteria are essential for making the story testable and for reducing confusion during development.

# 3. Product Backlog

## Evidence
The product backlog was created from the team’s agreed work and prioritised using MoSCoW.

### Must-have items
- Caddy onboarding
- Caddy profile
- Available tasks and task details
- Accept/reject task
- Customer homepage and task posting
- Accessible navigation
- Database creation and connection
- Administrator dashboard and verification requirements

### Should-have items
- Reviews and ratings
- Payment functionality
- Task monitoring and dispute management
- Customer support

### Could-have items
- Notifications
- Earnings feature

The priorities were ordered around trust and safety first, which is why verification and approval features came before convenience features.

## Reflection
The backlog changed as the team learned more about the system, especially when verification, ratings, and payments became clearer requirements. This showed me that a backlog is not fixed; it should be refined as the product becomes better understood. The main lesson was that prioritisation should be based on trust, dependency, and business value, not only on ease of implementation.

# 4. Sprint Backlog

## Evidence
We worked in four weekly sprints:

### Sprint 1 (14–17 July)
Goal: complete the Caddy/Helper user story
- Caddy onboarding
- Profile requirements
- Available tasks and task details
- Accept/reject workflow
- Trust and safety considerations

### Sprint 2 (21–24 July)
Goal: complete the wireframes
- Homepage layout
- Caddy profile structure
- Consistent wireframe criteria

### Sprint 3 (28–31 July)
Goal: add functionality and test the design
- Homepage functionality
- Helper and client page functionality
- Flow testing

### Sprint 4 (4–7 August)
Goal: create and connect the database
- Database creation
- Database connection
- Application integration

## Reflection
The sprint structure made the project manageable because each week had a clear goal. It also helped us keep momentum and avoid mixing unrelated tasks together. The main challenge was the database sprint, where connection problems took longer than expected. I learned that unfamiliar technical work needs more buffer time and should be planned with some flexibility.

# 5. Agile Logbook

## Evidence
The logbook records daily stand-ups and weekly walkthroughs for the full project period. It contains:

- Daily stand-up questions:
  - What did I complete?
  - What do I plan next?
  - What is blocking me?
- Team walkthrough questions:
  - What must we do to advance the work?
  - Is anyone working outside the board?
  - What must we finish as a team?
  - What is blocking the flow?

The logbook covers the four weeks from 14 July to 7 August and shows the project evolving from planning, to design, to implementation.

## Reflection
Keeping the logbook helped me become more aware of my progress and the issues affecting the workflow. It also taught me to write honest reflections about risk and blockers instead of only positive updates. The repeated problems I identified were complexity, team alignment, and technical uncertainty, and these were all issues that the Agile process helped manage.

# Connect: Bringing the Portfolio Together
The project followed a clear Agile flow:

- The team charter defined the values and guiding rules.
- The user stories translated those values into work from the user's perspective.
- The product backlog prioritised the features and tasks.
- The sprint backlog broke the work into manageable weekly goals.
- The logbook recorded what happened day by day and exposed the same risks that the charter was meant to manage.

This shows that the project was not only built, but also planned, reviewed, and improved using Agile methods.
